## The three axes

### Codebase

The repository contains no code yet.

- P1 (Phase 1 reality check): no conflicts. The repository has 4 commits and no code, and nothing references the decision's old path `docs/2026-10-25-go-pwr-design.md`. P1 also read commit ca813c6, the review-response commit (+48/-8).
- P3: a probe module that uses every library call the decision needs cross-compiles cleanly with `GOOS=linux GOARCH=arm GOARM=6 CGO_ENABLED=0`. The result is a static ARM EABI5 ELF of 4.1 MB, or 2.8 MB stripped, and `go vet` is clean. The library's `go.mod` requires go 1.25.0, so building with go1.24.3 under `GOTOOLCHAIN=local` fails. On the Mac, `ble` builds only with cgo, through the CoreBluetooth backend (P3-9).

### Architecture

Decision 0001 is the first decision, so no prior decisions are in force.

- P1: the core decision is "sound, small and cohesive": a read-only status tool, a pure parse/format core, one BLE package and a fixed JSON contract. It is one tool, so it needs no split. P1 also said the review round added implementation detail that belongs in implementing issues: the flag.Value mechanism, the 250 ms constant, the integer-arithmetic claim and the ble buffer semantics. The decision should keep only the observable contract and the principle (P1-7, P1-8, P1-9).
- P3: the decision's `ble` API sketch (`Connect(ctx, mac)`, `Read(ctx)`, `Close`) can be implemented on the library, but it "isn't a thin wrapper". P3-1, P3-2 and P3-6 put real logic in `ble`. No library call takes a context or a timeout, so the timeout budget is enforced by abandoning calls and cleaning up afterwards, not by cancellation (P3-2).
- P2: the guarantee that go-pwr sends nothing but the status request is "otherwise sound" (P2-6). The app drops notifications when no command is pending, which matches the decision's rule of dropping notifications outside a `Read`.

### Direction

- P1: the JSON output drives an automated shutdown, and the questions that matter most for that use are undecided: which device is trusted, whether a well-formed but wrong reply is caught, what exit status a signalled one-shot returns, and how two consumers share a controller that takes one connection (P1-1 to P1-4).
- P1 and P2 both said that `soc_pct` must not be what a shutdown keys on, and that consumers should use `battery_v` (P1-5, P2-1).
- P2: the transport is well supported (`" "` to FFF2, notifications on FFF1, ASCII `;` fields), and so are the core decoded fields (indices 0, 2, 9, 11, 12, 16, 17 and 19). What needs fixing before the JSON drives a shutdown is the meaning of `soc_pct`, which app build was used as ground truth, and the description of how a reply is judged complete.
- P3: the decision can be built with this library on this platform. What it says about timing and ordering does not hold up as written.
